# MConnect: проверка плохой сети — 2026-10-19

Это исходное исследование до изменения плагина. Реализация и последующие
проверки находятся в [RELIABLE_STREAMING.md](RELIABLE_STREAMING.md).

Повод: пользователь сообщил о щелчках, треске и коротких пропаданиях звука
при слабом Wi-Fi; задержка для этого сценария менее важна. Пользователь выбрал
сначала проверить плохую сеть, отложив физический тест по кабелю.

Проверка выполнена без DAW, установки новой версии и изменений сетевых
настроек macOS. Производственный код не менялся. Использованы установленный
AU, программный стереосигнал, настоящий Chromium/WebRTC/Opus и UDP-прокси.
Сам радиоканал и конкретный роутер пользователя не проверялись.

## Метод

`tests/network-impairment.cjs` переписывает ICE-кандидаты только тестового
браузера и пропускает зашифрованные пакеты через две локальные UDP-точки.
Прокси сохраняет сигналинг, STUN и DTLS; ухудшение применяется к настоящим
RTP/SRTP-пакетам. В браузере не подменяется `getStats()`.

Три этапа каждого прогона: нормальная сеть, ухудшение, восстановление.
На каждом этапе ожидание не менее десяти секунд. Проверяются поступление
медиа в контрольном окне и фактическое число испорченных прокси пакетов;
сохраняются настоящие счётчики браузера и работающий AudioContext.

- Потери: детерминированный генератор отбрасывает примерно 10% RTP-датаграмм.
- Джиттер: каждая пятая RTP-датаграмма задерживается на 350 мс и приходит
  не по порядку. В этом сценарии прокси ничего не уничтожает.
- Эксперимент NACK: тестовый браузер добавляет согласование повторной
  передачи в оба SDP и задаёт минимальную подсказку буфера 100 мс. Нативный
  отправитель уже содержит `RtcpNackResponder` и хранит до 512 пакетов.
  Это исследование протокола; настоящие SDP установленного плагина не менялись.
- Эксперимент буфера: тестовый браузер задаёт подсказку не ниже 500 мс.
  Это подсказка браузеру, а не гарантия заданной сквозной задержки.

Новые зависимости не добавлялись: используются существующий Playwright
1.62.1 и встроенный `node:dgram`. Настройка потерь через Chrome CDP в этой
среде не изменила входящее RTP-аудио, поэтому такой прогон не принят за
доказательство ухудшения сети.

## Результаты

Показатель ниже — доля аудиосэмплов, для которых браузер применил маскировку
нехватки данных (`concealedSamples / totalSamplesReceived` за интервал).
Это не процент слышимых щелчков и не оценка качества на слух.

| Сценарий | Текущий приёмник | Тестовый вариант |
| --- | --- | --- |
| Около 10% реальных потерь RTP | 6,157% маскировки | 0,229% с NACK и буфером от 100 мс |
| Каждый пятый пакет задержан на 350 мс | 17,320% маскировки | 0% с буфером от 500 мс |

В прогоне потерь текущий вариант получил 906 пакетов, прокси отбросил
102 из 1009. В эксперименте NACK прокси отбросил 117 из 1131 датаграммы,
включая повторные попытки; 107 уникальных ранее отброшенных пакетов затем
были действительно переданы повторно. Итоговый прирост счётчика потерянных
RTP-пакетов у браузера составил ноль, но небольшая маскировка сохранилась.

При джиттере текущий вариант получил 250 задержанных датаграмм, вариант
с большим буфером — 201. Небольшое временное увеличение `packetsLost`
при опозданиях уменьшилось после прихода пакетов; это не постоянная потеря
датаграмм. Во всех четырёх прогонах контрольное и заключительное окна
имели нулевую маскировку, соединение оставалось подключённым.

Полные данные: [машинный отчёт](validation/poor-network-2026-10-19.json).
Проверенный AU-сервер сообщал `/info.version = 0.1.6`, тогда как установленный
`Info.plist` содержал 0.1.7. В отчёте сохранены оба значения; проверка
согласованности пакета в эту задачу не входила.

## Условия корректного стенда

Скрытый программный хост без настоящего аудиоустройства получил от macOS
фоновые ограничения таймеров. В таком состоянии измерялись около 18 RTP/с
и 38176 отброшенных входных фреймов за секунду ещё без ухудшения UDP.
Эти прогоны отброшены как непригодные для сравнения сети.

После загрузки существующей тестовой `MConnectBrowserTiming.dylib` также
в процесс хоста измерены 101 RTP/с, нулевое отбрасывание очереди источника
и нулевая очередь отправителя. Финальные четыре прогона выполнены в этой
конфигурации. Библиотека меняет политику таймеров только тестового процесса;
она не входит в плагин и не меняет системные настройки.

## Повторение

Подготовьте тестовые цели и переменные Playwright по разделу
[повторения установленной проверки](VALIDATION_INSTALLED_0.1.5.md#повторение).
Все каталоги репозитория, `TMPDIR`, браузеров, кешей и результатов должны
находиться на `/Volumes/D`. Команды ниже запускаются из корня репозитория.
В первом терминале:

```sh
mkdir -p output/poor-network/tmp
export TMPDIR="$PWD/output/poor-network/tmp"
export MCONNECT_TEST_TIMING_LIBRARY="$PWD/build/libMConnectBrowserTiming.dylib"
export MCONNECT_INSTALLED_HOST="$PWD/build/MConnectInstalledHarness_artefacts/Release/MConnect installed test host.app/Contents/MacOS/MConnect installed test host"
DYLD_INSERT_LIBRARIES="$MCONNECT_TEST_TIMING_LIBRARY" \
  "$MCONNECT_INSTALLED_HOST" \
  --plugin "$HOME/Library/Audio/Plug-Ins/Components/MConnect.component" \
  --no-editor --seconds 600 \
  --info "$PWD/output/poor-network/info.json" \
  --control "$PWD/output/poor-network/control.json"
```

Во втором терминале с теми же переменными, когда появился `info.json`,
выполните четыре команды последовательно. Возврат каждой команды должен
быть нулевым; текст `FAIL` после JSON означает непригодный прогон:

```sh
node tests/network-impairment.cjs output/poor-network/info.json > output/poor-network/loss.json
MCONNECT_PROBE_NACK=1 MCONNECT_PROBE_BUFFER=100 \
  node tests/network-impairment.cjs output/poor-network/info.json > output/poor-network/loss-nack.json
MCONNECT_PROBE_JITTER=1 \
  node tests/network-impairment.cjs output/poor-network/info.json > output/poor-network/jitter.json
MCONNECT_PROBE_JITTER=1 MCONNECT_PROBE_BUFFER=500 \
  node tests/network-impairment.cjs output/poor-network/info.json > output/poor-network/jitter-500.json
```

После проверки закройте тестовый хост либо отправьте `{"quit":true}` через
его control-файл. При повторении используйте новые info/control-файлы,
чтобы не подключиться к URL завершённого экземпляра.

## Вывод для доработки

Больший буфер помогает опоздавшим пакетам, но сам не восстанавливает
уничтоженные пакеты. Для устойчивого варианта стоит проверить штатное
согласование NACK с отправителем и более широкий автоматический запас
буфера при плохой сети. Это можно сделать без новых кнопок и второго
кодирования звука; повторно отправляются уже закодированные пакеты.

Ни один эксперимент не устанавливался пользователю. Перед включением
в выпуск необходимы проверки настоящего согласования SDP без тестовой
подмены, WebKit/iPhone и длительная работа на слабом Wi-Fi.

USB-сеть возможна отдельно от аудиоустройства DAW. Apple описывает
[подключение Mac к iPhone по USB](https://support.apple.com/en-my/guide/mac-help/mchl7594e36f/mac)
и [режим модема по Bluetooth](https://support.apple.com/guide/iphone/iph45447ca6/ios).
Это сетевые соединения, отличные от прямой передачи аудио как на Bluetooth-наушники.
Физическая работа MConnect по USB и Bluetooth в этой задаче не проверялась.
